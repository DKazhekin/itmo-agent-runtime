# Монтирование папки клиента в Linux

Для удалённого доступа выбран SSHFS на Linux поверх SFTP-сервиса клиента и обратного SSH-туннеля. Отдельный прототип подтвердил чтение и запись Mac ↔ Linux, права и поведение при обрыве: 17 проверок прошли. В продукт этот механизм ещё не интегрирован; текущий клиент передаёт снимок синтетических исходных файлов.

Mac создаёт `from_mac.txt`, Linux читает его через `fuse.sshfs`, затем записывает `from_linux.txt`, который независимо проверяется на Mac. Общая папка виртуальной машины не участвует в передаче этих файлов.

Для интеграции требуется менеджер состояния монтирования. При потере соединения он должен запрещать новые инструменты и завершать текущую операцию ошибкой. Обрыв записи не доказывает, что запись не произошла; автоматически повторять её нельзя. После закрытия туннеля SSHFS может размонтироваться самостоятельно: без проверки состояния последующая запись попадёт в лежащий под монтированием локальный каталог сервера.

## Сравнение трёх вариантов

| Критерий | SSHFS + SFTP + обратный SSH | WebDAV + rclone | NFS с защищённым транспортом |
| --- | --- | --- | --- |
| Закреплённый источник | SSHFS `sshfs-3.7.6`, commit `7a2d988775446ebe7af9b01c99b3b8e86bddb05a`; AsyncSSH `v2.24.1` | rclone `v1.75.2`, commit `be8d6044eacb843b74d335db0c5fbe09222031fe` | Публичный Apple NFS `NFS-343.100.5`, commit `93733ffccece4daee73bf6306b291d1ae69130c0`; установленная macOS 26.4.1. Это версия изученного исходника, соответствие исходника бинарнику macOS не установлено |
| Роль Mac | Приложение предоставляет только выбранную папку по SFTP, то есть файловому протоколу SSH. Сам Mac ничего не монтирует | Приложение предоставляет папку по WebDAV — расширению HTTP для работы с файлами | Системный NFS-сервер экспортирует папку; обычно нужны настройка экспортов и системные полномочия |
| Роль Linux | SSHFS монтирует SFTP через FUSE — интерфейс файловых систем в пользовательском процессе | rclone монтирует WebDAV через FUSE и слой файлового кэша | Клиент ядра Linux монтирует NFS — сетевую файловую систему |
| Защита | Проверенные ключи обеих сторон; один ключ на сессию; обратный туннель допускает исходящее соединение Mac. Сервис не предоставляет shell | HTTPS с проверкой сертификата и аутентификацией либо защищённый туннель. По умолчанию `serve webdav` предоставляет HTTP без входа: настройки безопасности обязательны | Сам `sec=sys` не шифрует транспорт. Рассматривается VPN, то есть защищённая виртуальная сеть, или Kerberos `krb5p`. Linux RPC-over-TLS не означает поддержку на Mac; совместимость не доказана |
| Права | `default_permissions`, отображение пользователя через `idmap=user`, контроль прав на стороне сервиса. `ro` задаёт режим монтирования только для чтения | Права, владелец и маска в слое rclone задаются отдельно; нельзя считать их точной копией прав исходной папки. Режим только чтения есть | Идентификаторы пользователей и групп требуют согласования; Apple поддерживает `maproot`, `mapall`, `ro`, `sec`. Отображение администратора не заменяет аутентификацию |
| Файловая семантика | Близка к обычным файлам, но расширения SFTP влияют на rename/hardlink; кэши влияют на видимость. В прототипе выключены кэш содержимого и каталогов | Для произвольной записи обычно нужен `--vfs-cache-mode writes/full`; выгрузка может произойти после закрытия файла. WebDAV не передаёт обычные symlink, plain WebDAV ограничивает время изменения и хеши | Богаче семантика блокировок и файловых операций, но больше связей с ядром, службами и политикой экспортов |
| Обрыв | Без настроенных keepalive операции могут зависать. В прототипе ошибка через 2.82 секунды; восстановление отдельным монтированием | Кэш и повторные выгрузки усложняют момент подтверждения записи и конфликты с редактором Mac | `hard` повторяет запросы без конечного срока; `soft` ограничивает ожидание ценой риска повреждения данных |
| Совместимость Apple Silicon | Доказана живая связка macOS arm64 → Ubuntu aarch64; macFUSE на Mac не нужен | Сервис Mac + монтирование Linux не требует macFUSE на Mac. Обратное направление через `rclone mount` имеет дополнительные варианты macFUSE/FUSE-T/NFS | Системная поддержка на Mac есть, но безопасный экспорт и туннелирование нескольких служб требуют отдельной проверки |
| Поддержка и сложность | Узкий и объяснимый путь, однако у SSHFS ограниченные ресурсы сопровождения. Старый 3.7.3 из VM исключён из выбора | Активные релизы, много поддерживаемых хранилищ и настроек, но для папки с кодом это увеличивает поверхность поведения | Поддержка ядрами и ОС, но самая тяжёлая настройка для переносимого пользовательского клиента |
| Доказательства здесь | Настоящее монтирование и 17 проверок прошли; все попытки сохранены | Изучены документация и исходник указанной версии; запуск не выполнялся | Изучены исходники Apple, документация Linux и локальные страницы руководства Mac; системный сервер не включался |

## Проверка версии и исходника

Установленный SSHFS 3.7.3 недостаточен для выбора: [релиз 3.7.6](https://github.com/libfuse/sshfs/releases/tag/sshfs-3.7.6) исправляет CVE-2026-47187 — выход через вредоносную символическую ссылку — и CVE-2026-48711 — внедрение аргументов. [Сообщение об уязвимости ссылок](https://github.com/libfuse/sshfs/security/advisories/GHSA-pjv6-2c3f-r357) указывает затронутые версии до 3.7.5 включительно. В исходнике `sshfs.c` проверены `contain_symlinks` и `sshfs_readlink`: абсолютные цели и `..` не должны уходить клиенту как разрешённые ссылки. Поддержка проекта ограничена, даже при наличии новых релизов; это риск следующего этапа.

Вместо замены системного пакета собран SSHFS 3.7.6 в `/tmp/itmo-sshfs-build/build/sshfs`; хеш SHA-256 архива исходников: `67a3e166a39b07708497ee0aee308547dba386053cf8d816b4ce8a9b3066a6ce`. Linux использовал FUSE 3.14.0, GLib 2.80.0, GCC 13.3.0, Meson 1.3.2. Тег upstream не подписан; хеш закрепляет полученные байты, а не заменяет доверие к источнику.

В [AsyncSSH 2.24.1](https://github.com/ronf/asyncssh/releases/tag/v2.24.1) непосредственно изучены `SFTPServer.map_path`, `readlink`, `symlink`, `reverse_map_path` и проверка ключей. Виртуальный `chroot` сам по себе не гарантирует запрет всех существующих внешних ссылок. Прототип добавляет проверку реального пути, запрещает создание ссылок и сохраняет только безопасные относительные цели. Код находится в [server.py](../../prototypes/mounting/server.py). Проверка пути уязвима к гонке с локальным процессом: для реальных папок требуется защита на уровне открытых дескрипторов либо операционной системы.

В rclone изучены `OptionsInfo` и `Object.Open/Update`: настройки показывают отдельные разрешения `file_perms` и `dir_perms`, кэш каталога, задержку выгрузки `vfs_write_back`; WebDAV передаёт содержимое через HTTP. Для редактирования кода более сложное подтверждение записи перевешивает удобство HTTP. Это инженерный вывод по требованиям, а не результат замера производительности.

В исходнике [Apple nfsd.c](https://github.com/apple-oss-distributions/NFS/blob/NFS-343.100.5/nfsd/nfsd.c) проверены `nfsd_server_thread` и `nfsd_accept_thread`: первый вызывает `nfssvc(NFSSVC_NFSD)`, второй передаёт принятые сокеты в ядро через `NFSSVC_ADDSOCK`. Это подтверждает тесную связь варианта с системной службой и ядром; перенос файлового сервиса целиком в обычный процесс клиента здесь не получается.

## Живой прототип

Команды воспроизведения: [prototypes/mounting/README.md](../../prototypes/mounting/README.md), [prepare_linux.sh](../../prototypes/mounting/prepare_linux.sh), [run.py](../../prototypes/mounting/run.py). Машиночитаемый окончательный результат: [attempt-3/result.json](../../evidence/mounting/attempt-3/result.json). В нём сохранены результаты команд и длительности; локальные пути и идентификаторы ключей в опубликованной копии обезличены.

```text
Mac: временная папка → SFTP 127.0.0.1:<port>
                         ↑
Mac инициирует SSH -R → Linux 127.0.0.1:<port>
                         ↑
Linux SSHFS → /tmp/itmo-mount-*/mounted (fuse.sshfs)
```

Пользовательские данные не экспортировались. На каждый запуск создавались новые ключи; проверка ключа SFTP-сервера включена. Ключ виртуальной машины получен через существующий канал управления Colima и закреплён отдельно; настройки с отключённой проверкой из файла Colima переопределены. Системный Remote Login на Mac не включался. Папка Linux находится под `/tmp`, а `findmnt` зафиксировал `fuse.sshfs`; virtiofs не является путём передачи тестовых файлов.

| Проверка | Фактический результат |
| --- | --- |
| Запись Mac → чтение Linux; запись Linux → чтение Mac | Содержимое проверено программно с обеих сторон |
| Изменение файла Mac после монтирования | Linux получил обновлённый текст |
| `chmod 0600` с Linux | Mac увидел режим 0600 |
| Запись в файл 0444 и внешние ссылки | Код ошибки 13, доступ запрещён; внешняя фикстура не изменилась |
| Только чтение (`ro`) | Создание файла отклонено кодом 30; файла на Mac нет |
| `../../outside.txt`, `/../../outside.txt`, внешняя ссылка и ссылка-каталог через SFTP | Все четыре запроса отклонены |
| Относительная ссылка внутрь папки | Чтение разрешено |
| Незарегистрированный ключ и запрос shell | Оба отклонены |
| Зависший SFTP (`SIGSTOP`) | Ошибка ввода/вывода `EIO` за 2.818 секунды; внешний предел проверки 10 секунд |
| Явное повторное монтирование | Новый файловый дескриптор успешно прочитал прежнее содержимое |
| Закрытие обратного туннеля | SSHFS автоматически размонтировался; чтение вернуло `ENOENT` за 0.000030 секунды. Это не доказательство атомарности записи |
| Очистка | Монтирование отсутствует, временные папки и ключи удалены, фоновые процессы завершены |

Таймеры эксперимента: `ServerAliveInterval=1`, `ServerAliveCountMax=2`, `ConnectTimeout=3`; это не обещание времени реакции любой сети. Автоматический `reconnect` и повтор записи отключены. Первый неуспешный запуск выявил неверное разрешение относительной ссылки в стандартном виртуальном chroot AsyncSSH; исправлен метод `readlink`. Второй неуспешный запуск показал самостоятельное размонтирование после EOF; проверка уточнена, чтобы различать ошибку файловой системы и исчезновение монтирования. Оба журнала сохранены, успехом они не считаются.

## Границы проверки

Прототип работает с контролируемыми синтетическими файлами. Проверка реального пути не защищает от одновременной подмены ссылки локальным процессом; для произвольных папок нужны операции через открытые дескрипторы или изоляция средствами операционной системы.

Не проверены одновременные правки с двух сторон, конфликты регистра и Unicode, блокировки, атомарная замена, гарантии `fsync`, запись при обрыве, большие файлы, подключение песочницы к FUSE, отдельный физический сервер и смена сети. Результат не является гарантией синхронизации или сохранности реальной пользовательской папки.

Команды подготовки и очистки приведены в [руководстве прототипа](../../prototypes/mounting/README.md). Сборка SSHFS не заменяет системный пакет. Итоги всех трёх попыток, включая две неуспешные, сохранены в [публичном наборе результатов](../../evidence/README.md).
