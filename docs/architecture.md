# Архитектура первой версии

Система состоит из четырёх серверных служб, клиента командной строки и отдельного контейнера на каждую сессию. Модель выбирает инструменты, управляющий цикл проверяет и передаёт вызовы, а песочница исполняет их с ограниченными полномочиями. Оба протокола имеют версию 0. Результаты экспериментов и проверок собраны в [отчёте первого этапа](checkpoint-1.md).

## Компоненты и данные

| Компонент | Код | Интерфейс и полномочия |
| --- | --- | --- |
| Клиент командной строки | client/cli.py | Mac; адрес и Bearer-токен; создаёт сессию, отправляет задачу, читает события с курсором, получает файлы, освобождает сессию |
| Gateway | runtime/gateway.py | Единственная опубликованная точка 127.0.0.1:8080; проверяет токен, перенаправляет разрешённые маршруты в харнес |
| Управляющий цикл | runtime/harness.py | Контекст, проверка вызовов, ограничения шагов и времени, остановка; HTTP к модели и менеджеру; SQLite /state |
| Менеджер | runtime/sandbox.py | Единственный доступ к Docker socket; создание, команды, сбор и удаление контейнеров; журнал операций вне /work |
| Модельный посредник | runtime/proxy.py | Единственный ключ провайдера; mock фиксирует демонстрацию, real передаёт сообщения удалённой модели через HTTPS |
| Песочница | Dockerfile.sandbox | Python3.12 и shell; user1000, сетьnone, без Docker и ключей, лимиты; /work и /tmp в tmpfs |
| Запускатель БАФ | baf/run.py | Чистая сессия на задачу; сбор файлов и журналов; независимые check.py выполняются вне песочницы |

Серверные службы собираются из одного набора исходников в отдельные образы. Сеть control помечена internal; gateway дополнительно имеет ingress для публикации порта, модельный посредник — model для доступа к провайдеру. Песочницы вообще не подключены к этим сетям.

## Один запрос

Клиент сначала проверяет `/health`: готовность, `model_mode` и точное имя `model`. По умолчанию он ожидает `mock`; реальный вызов требует `--mode real --model <точное-имя>`. Несовпадение останавливает клиент до создания сессии. Клиент передаёт только выбранные синтетические fixture-файлы как карту путь→base64. Менеджер проверяет пути и пишет их через stdin доверенного Python в /work нового контейнера. Это временный снимок для первого чекпоинта; настоящая работа с удалённой папкой не реализована этим API.

Управляющий цикл перед принятием новой задачи сверяет `expected_mode` и `expected_model` с настройками посредника. Посредник повторяет проверку перед каждым обращением к провайдеру. Например, запрос с ожидаемым `mock` к серверу в `real` получает отказ до модельного вызова; случайная смена серверной настройки не превращает демонстрацию в платный прогон.

Управляющий цикл отправляет инструкцию и схемы трёх инструментов модели. Модель выбирает ReadFile, WriteFile или RunCommand. Менеджер повторно проверяет аргументы и запускает инструмент только в контейнере. stdout/stderr/exit_code возвращаются модели отдельными полями. Общая инструкция и описание RunCommand объясняют, что существующие программы и наборы тестов следует запускать напрямую, без объединения вывода и допечатывания кода завершения: иначе результат оболочки может скрыть исходный код программы. В реальном режиме посредник требует точного совпадения имени модели в ответе провайдера и проверяет завершённость ответа: `stop` с текстовым ответом без вызовов либо `tool_calls` с непустым списком вызовов. Обрезанный, отфильтрованный или иной незавершённый ответ приводит к `model_error` с `incomplete_response`; его инструменты не исполняются. Допустимый ответ без вызовов завершает цикл, но только независимая проверка устанавливает правильность файла.

Пример: config/app.yaml содержит 8137; модель читает файл, запрашивает запись answer.txt, завершает ответ. Проверка читает answer.txt отдельно и сравнивает с 8137, не анализируя обещание модели.

## Доказательства модельного прогона и расходы

Событие `model` сохраняет режим, сообщённое провайдером имя модели и доступные неотрицательные целые счётчики токенов. Оно записывается и перед завершением с ошибкой несовпадения модели или незавершённого ответа. Запускатель БАФ требует подтверждения режима и модели по событиям; при ошибке исполнения или несовпадении прекращает запуск оставшихся задач и сохраняет причину и список `not_run`.

Для реального запуска число токенов суммируется только при успешном завершении управляющего цикла, обработке результатов без исключений и полных счётчиках каждого вызова. Иначе `tokens_in` и `tokens_out` равны `null`, а `tokens_complete` — `false`; отрицательный вердикт проверки файлов сам по себе не стирает полные данные. Ноль записывается для подтверждённой имитации. Поле `budget_limit` в файле сведений о модели сохраняет параметр эксперимента; само по себе оно не учитывает стоимость и не ограничивает расходы. Для выбранного профиля OpenRouter предел обеспечивает отдельный постоянный журнал резервирования. Его настройка описана в [руководстве модели](reference/model.md).

## Сессия, повторы и отмена

Сессия — один контейнер; задача — один request_id; действие — один operation_id. В сессии одновременно работает одна задача. Идентификаторы задаёт доверенный код; модель выбирает только инструмент и аргументы. SQLite хранит отпечаток и итог; события имеют seq для продолжения чтения. Один и тот же идентификатор с другим содержимым отвергается 409. Повтор существующего действия возвращает состояние без исполнения.

Отмена/таймаут удаляют контейнер целиком: даже дочерний процесс с новым сеансом прекращается. Временные рабочие файлы теряются, продолжить отменённую сессию нельзя. После перезапуска менеджера контейнеры его пространства имён удаляются, сессии освобождаются, незавершённые операции получают ошибку неопределённого исхода. Автоматический повтор записи запрещён. После перезапуска харнеса незавершённые задачи завершаются ошибкой; контекст между разными задачами не сохраняется.

Доверенные файловые помощники запускаются абсолютным Python с -I -S, поэтому json.py из /work не может подменить сбор результатов. Сбор файлов и инициализация также имеют конечное время. Входное сообщение ограничено 8 МБ, рабочая tmpfs — 64 МиБ. Сбор артефактов ограничен 4 МиБ на файл, 8 МиБ суммарно и 4096 файлами; разреженные файлы сверх этих размеров отвергаются. Вывод команды также ограничен. Оба протокола проверяются по схемам. Сохранённая проверка успешного реального прогона включает 322 события; результаты в [матрице](checkpoint-1.md) и [отчёте проверки](../evidence/verification/real-run-audit.json).

## Монтирование: проверено отдельно, интеграция запланирована

[Прототип](../prototypes/mounting/README.md) установил настоящую SSHFS между Mac и Linux через исходящий обратный SSH-туннель. Проверены двусторонние изменения, права, запреты и обрыв. Результат 17 проверок сохранён. Это не общая папка VM.

Следующий этап: менеджер жизненного цикла монтирования, защита от исчезновения mountpoint и гонок файловых путей, подключение монтирования к песочнице, защита .git и служебных файлов, конфликты и оборванная запись. Полный интерфейс клиента также запланирован. Текущие ограничения не выдаются за готовое монтирование продукта.

## Контроль расходов выбранного OpenRouter

Для DeepSeek V4.1 Flash 1017 посредник закрепляет режим high, адрес DeepInfra `deepinfra/fp8` с восьмибитной точностью с плавающей запятой (FP8), максимум 4096 генерируемых токенов и цены не выше 0,30/1,20 доллара за миллион входных/выходных токенов. Маршрутизация разрешает только этот адрес (`only`), запрещает переход к другим поставщикам (`allow_fallbacks: false`) и сбор данных (`data_collection: "deny"`); ответ обязан назвать поставщика `DeepInfra`. Профиль допускает только текст до 256 КиБ и обычные функции клиента. Журнал runtime/budget.py хранится в model-state от пользователя 1000; перед запросом атомарно резервируется 0,35 доллара. Суммы хранятся целыми миллионными долями доллара, подтверждённый расход округляется вверх. Неизвестный исход сохраняет весь резерв. При неожиданной модели/поставщике, BYOK или превышении резерва последующие вызовы блокируются постоянно.

Лимит задаётся при однократной инициализации журнала; runtime сам не создаёт бюджет и не меняет его предел. После удаления тома реальные запросы отказывают, а не получают новый остаток. Контроль относится к списаниям OpenRouter по проверенному профилю; комиссия покупки кредитов и другие каналы оплаты в него не входят. Перед платным запуском проверяются доступные метаданные оплаты. Нулевой прошлый расход собственного ключа поставщика (BYOK, bring your own key) не доказывает отсутствия такого ключа. Первый и каждый последующий ответ должны содержать `usage.is_byok=false` для зачёта фактической стоимости; при `true` журнал сохраняет полный резерв и блокирует дальнейшие вызовы. Произвольное нарушение заявленного поставщиком договора оплаты этой защитой не исключается. Это не подмена общего budget_limit из отчёта: отчёт хранит сведения, отдельный журнал обеспечивает контроль. Прочие поставщики не имеют этого профиля.
